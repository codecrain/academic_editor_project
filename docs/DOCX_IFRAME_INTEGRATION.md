# DOCX iframe integration

This document describes the current DOCX iframe behavior and the proposed
minimum-complexity contract for host-owned context-menu actions. Proposed
messages in this document are a design contract, not an implemented runtime
feature.

The DOCX editor remains a separate Collabora/WOPI runtime. Product
authentication, tenant policy, business APIs, and user data remain in the
embedding service.

## Implementation status

Implemented today:

- The gateway renders an outer DOCX wrapper containing the Collabora editor as
  a nested iframe.
- The wrapper relays postMessage traffic between its parent and the nested
  editor after checking the sending window and exact origin.
- Collabora supports its existing postMessage commands, including
  `Host_PostmessageReady`, `Action_Copy`, `Action_Paste`, `Action_Save`,
  `Send_UNO_Command`, `Insert_Button`, `Insert_ContextualButton`, and the
  product `Get_Document_UI_State` diagnostic response.
- Native DOCX upload and WOPI save paths preserve the uploaded OOXML package
  rather than reconstructing it in the browser.

Not implemented in this pass:

- Host-owned entries in the right-click context menu.
- `Host_Tlooto_ContextActions`, `Tlooto_ContextAction_Requested`, or
  `Host_Tlooto_ContextAction_Result` handlers.
- Runtime validation, dispatch, or application of the proposed result types.
- A host-side ServiceV2 dispatcher. That code belongs to the private service
  repository and must be verified there.

`Insert_Button` and `Insert_ContextualButton` do not add right-click menu
entries. They cannot be treated as evidence that the proposed context-menu
feature exists.

## Current iframe and origin topology

The production topology has two iframe boundaries:

```text
ServiceV2 page (service origin)
  -> gateway DOCX wrapper (gateway public origin)
       -> Collabora editor iframe (gateway public origin through the proxy)
```

The outer wrapper is generated by `renderDocxPage()` in
`editor_server/editor-gateway.mjs`. It derives the service origin from
`document.referrer`, then applies these checks:

- service to wrapper: `event.source === window.parent` and an exact service
  origin match;
- nested editor to wrapper: `event.source === editorFrame.contentWindow` and
  `event.origin === window.location.origin`.

The wrapper response also sets `Content-Security-Policy: frame-ancestors
'self' ...` from `EDITOR_GATEWAY_FRAME_ANCESTORS`. Every cross-origin host must
be explicitly configured there; the policy applies to the wrapper itself as
well as the proxied Collabora page.

The WOPI `PostMessageOrigin` sent to Collabora is therefore the **gateway
public origin**, not the ServiceV2 origin. Collabora posts to its immediate
parent, the gateway wrapper. The wrapper then relays the message to the
ServiceV2 parent using the exact service origin.

A host integration must send messages to the wrapper iframe window using the
gateway action URL origin and must accept replies only when both conditions
hold:

```js
event.source === editorIframe.contentWindow
event.origin === new URL(actionUrl).origin
```

The current wrapper stops relaying when `document.referrer` is empty. A host
must not apply `Referrer-Policy: no-referrer` to the editor navigation until a
signed parent-origin session claim replaces this dependency.

## Existing postMessage baseline

The host sends `Host_PostmessageReady` after the wrapper iframe loads and waits
for `App_LoadingStatus` with `Values.Status === "Document_Loaded"` before using
document commands. Messages should be JSON strings for compatibility with the
early Collabora readiness listener.

The existing `Action_Copy` command can request the current selection:

```json
{
  "MessageId": "Action_Copy",
  "Values": {
    "Mimetype": "text/plain;charset=utf-8"
  }
}
```

Collabora replies with `Action_Copy_Resp`. This proves that bounded document
context can cross the existing bridge, but the upstream response has no
request ID and should be limited to one in-flight request. The proposed custom
protocol below adds explicit correlation and stricter validation.

## Mixed page sizes and orientation

A DOCX page ratio is not a viewport or zoom property. WordprocessingML stores
page size, orientation, margins, columns, and section-break behavior in
`w:sectPr`. A document can contain paragraph-owned section properties followed
by a final body section property, so all native section properties must survive
upload, edit, save, and reopen.

The WOPI import path stores the uploaded DOCX bytes without reconstructing the
package. The structured DOCX API must follow the same rule:

- `read-json.sections[]` exposes every `w:sectPr` in native order.
- Every paragraph, table, and editable target reports its zero-based native
  section.
- `setPageSetup.section` targets one section. `"all"` is explicit and must not
  be inferred from a missing field.
- Updating one section preserves the other section properties and the original
  attributes on each `w:sectPr`.
- A release test saves, reopens, and compares every section's page size,
  orientation, margins, columns, and break type. A successful API response
  alone is not acceptance evidence.

If an imported document still renders every page with one ratio, download the
current WOPI file and inspect `word/document.xml` first. If the expected
`w:sectPr` values are absent, the layout was lost before rendering. If they are
present, treat the result as a native renderer regression and retain the exact
package as a fixture.

`Get_Document_UI_State_Resp.Values.PageGeometry` exposes the geometry actually
accepted by the Writer core, independently of the iframe width and zoom. The
unit is `twip`; `Rectangles` contains up to the first 500 `[x, y, width,
height]` entries, `Sizes` reports each distinct width/height and count, and
`Truncated` tells the host when the rectangle list was bounded. Compare these
values with `read-json.sections[].pageSetup` and a save/reopen artifact audit;
do not infer a paper-size defect from a narrow iframe screenshot alone.

## Proposed minimum-complexity context-action contract

The preferred first implementation uses the existing postMessage bridge to
advertise capabilities after readiness. It does not add a new WOPI property or
modify the Collabora C++ CheckFileInfo pipeline.

This choice keeps tenant and user policy in the host, avoids four duplicate
capability plumbing layers, and still fails closed because the browser only
renders actions explicitly registered for the current session.

### 1. Capability registration

After `Document_Loaded`, the trusted host sends:

```json
{
  "MessageId": "Host_Tlooto_ContextActions",
  "Values": {
    "protocolVersion": 1,
    "sessionNonce": "opaque-session-random-value",
    "capabilitiesRevision": 1,
    "actions": [
      {
        "id": "rewrite_formal",
        "label": "Rewrite formally",
        "contexts": ["text-selection"],
        "requiresWrite": true,
        "maxSelectionLength": 4000,
        "resultKinds": ["notification", "replace-selection"]
      }
    ]
  }
}
```

The editor replaces, rather than merges, the previous registry when
`capabilitiesRevision` increases. It rejects a reused nonce, a lower or equal
revision with different content, duplicate IDs, unknown fields, unsupported
contexts or result kinds, and descriptors outside the configured bounds.

Version 1 contexts are intentionally small:

- `text-selection`: an active text selection;
- `image-selection`: an active graphic selection;
- `table-selection`: reserved until a reliable native table-selection
  classifier and bounded table projection are implemented.

Read-only sessions never show an action with `requiresWrite: true`.

### 2. User request

When the user selects an allow-listed menu entry, the editor snapshots the
current context and emits:

```json
{
  "MessageId": "Tlooto_ContextAction_Requested",
  "SendTime": 1785177600000,
  "Values": {
    "protocolVersion": 1,
    "sessionNonce": "opaque-session-random-value",
    "requestId": "uuid",
    "actionId": "rewrite_formal",
    "selectionSnapshotId": "opaque-editor-generated-id",
    "context": {
      "kind": "text-selection",
      "selectedText": "bounded selected text",
      "selectionLength": 21
    }
  }
}
```

`selectedText` is present only for `text-selection`, must be plain text, and
must not exceed the action's `maxSelectionLength` or the editor-wide hard
limit. The editor permits only one in-flight request per session in version 1.
It cancels the request if the selection, document, permission, or registered
capability changes.

### 3. Host result

The host owns authentication and calls private service APIs with host-side
credentials. It returns a result to the same wrapper window and exact gateway
origin:

```json
{
  "MessageId": "Host_Tlooto_ContextAction_Result",
  "Values": {
    "protocolVersion": 1,
    "sessionNonce": "opaque-session-random-value",
    "requestId": "uuid",
    "selectionSnapshotId": "opaque-editor-generated-id",
    "status": "completed",
    "result": {
      "kind": "replace-selection",
      "mimeType": "text/plain;charset=utf-8",
      "data": "Replacement text"
    }
  }
}
```

Version 1 result kinds are:

- `notification`: bounded plain-text status shown by the editor;
- `open-panel`: bounded opaque reference handled by the host UI, not arbitrary
  HTML;
- `replace-selection`: bounded plain text applied only if the original
  selection snapshot is still current.

The editor rejects arbitrary JavaScript, arbitrary UNO commands, HTML, URLs
outside an explicit allow-list, unknown MIME types, stale selection snapshots,
unknown or completed request IDs, and result kinds not declared by the action.
A rejected or failed host operation uses the same envelope with
`status: "rejected"` or `status: "failed"` and a bounded user-safe message.

`replace-selection` is a live editor operation and must remain undoable. A
whole-document API mutation follows a different sequence:

1. Request `Action_Save` with notification enabled.
2. Wait for a successful `Action_Save_Resp`.
3. Read the current server-side document version.
4. Apply revision-bound document API commands.
5. Save and quality-check the artifact.
6. Ask the user to reload or reopen the committed revision.

The host must not run a whole-document API mutation concurrently with unsaved
iframe edits.

## Exact implementation extension points

No runtime files are changed by this documentation pass. A future
implementation should modify these existing paths:

1. `editor_docx/browser/src/map/handler/Map.WOPI.js`
   - Extend `_postMessageListener()` with strict handlers for
     `Host_Tlooto_ContextActions` and
     `Host_Tlooto_ContextAction_Result`.
   - Store the validated per-session action registry.
   - Require `e.source === window.parent` for custom messages in addition to
     the existing origin check.
   - Emit `Tlooto_ContextAction_Requested` through `_postMessage()`.
2. `editor_docx/browser/src/control/jsdialog/Control.ContextMenu.ts`
   - Add matching entries in `_amendContextMenuData()`.
   - Route `tlooto-action:<id>` callbacks in `_addMenu()` to a dedicated map
     event instead of passing them to `sendUnoCommand()`.
   - Use `TextSelections.isActive()` and
     `GraphicSelection.hasActiveSelection()` for version 1 visibility.
3. Selection extraction
   - Reuse the bounded `gettextselection` event pattern implemented by
     `fetchSelectedMarkdown()` in
     `editor_docx/browser/src/control/Control.AIChatSidebar.ts`, or factor the
     pattern into a small shared browser helper.
   - Do not reuse the upstream `Action_Copy` single boolean as a multi-request
     correlation mechanism.
4. `editor_server/editor-gateway.mjs`
   - Keep `renderDocxPage()` as the single wrapper relay; do not create a
     second bridge.
   - In a security-hardening change, bind an allow-listed parent origin into
     the signed editor session and emit `frame-ancestors` CSP on the outer
     wrapper. This should replace, not supplement indefinitely, the current
     `document.referrer` dependency.
5. Private ServiceV2 repository
   - Validate `event.source`, exact gateway origin, protocol version, nonce,
     request ID, action policy, payload bounds, current user, tenant,
     permission, and rate limit before dispatch.
   - Keep service bearer tokens and private API responses outside the iframe.

Adding `TlootoContextActions` to CheckFileInfo later is possible but is not the
minimum-complexity implementation. It would also require explicit parsing and
forwarding changes in `editor_docx/wsd/wopi/WopiStorage.hpp`,
`editor_docx/wsd/wopi/WopiStorage.cpp`, and
`editor_docx/wsd/DocumentBroker.cpp`; unknown CheckFileInfo fields do not reach
the browser automatically.

## Security requirements

- Complete the existing `Host_PostmessageReady` and `Document_Loaded`
  handshake before accepting capabilities.
- Use exact origins at both iframe boundaries. Never use `"*"` in product
  host code.
- Require both the expected window and exact origin before parsing data.
- Parse JSON defensively and validate a closed schema before dispatch.
- Treat the capability message as session-scoped authorization, not merely UI
  configuration.
- Generate unpredictable session nonces and request IDs; deduplicate completed
  and expired IDs.
- Bound action count, ID length, label length, selection length, result length,
  and total serialized message size.
- Permit one in-flight request in version 1, enforce a short timeout, and fail
  closed on selection or permission changes.
- Disable write actions in read-only mode.
- Never send bearer tokens, WOPI access tokens, storage credentials,
  unrestricted document bytes, arbitrary HTML, or unrestricted document
  projections through the custom channel.
- Audit action ID, user, document, decision, duration, and result status without
  logging selected or replacement text.
- Keep the existing general Collabora postMessage API compatible, but validate
  the custom channel independently instead of relying on the wrapper's relay
  checks alone.

## Required verification

Unit and contract tests must cover:

- malformed JSON and object payloads;
- wrong source window and wrong origin at both iframe boundaries;
- missing readiness, wrong protocol version, nonce mismatch, and stale
  capability revisions;
- unknown, duplicate, hidden, or disallowed actions;
- read-only sessions and write-only actions;
- oversized labels, selections, results, and total payloads;
- duplicate request IDs, multiple in-flight requests, timeout, and late result;
- changed selection, permission, or document state before a result arrives;
- unsupported context, result kind, and MIME type;
- attempted JavaScript, HTML, URL, and arbitrary UNO injection.

Browser acceptance must cover the real nested iframe topology:

1. Load an editable DOCX through the signed POST action URL.
2. Verify the readiness handshake and `Action_Copy` baseline.
3. Select text, open the native right-click menu, and verify that only the
   allowed action appears.
4. Capture the exact request payload in a host stub.
5. Return a replacement, verify its placement and formatting boundary, then
   undo it.
6. Save, download, reopen, and compare the committed DOCX.
7. Repeat negative cases for read-only mode, changed selection, spoofed origin,
   duplicate response, and timeout.
8. Verify image selection separately. Keep table actions disabled until their
   native context and bounded projection have dedicated acceptance evidence.

For whole-document mutations, acceptance requires save/reopen and artifact
inspection. A successful postMessage or API response alone is never sufficient.
